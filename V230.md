## 1. Friend invite gift: what the player sees

- The Friends sheet gets one line under the invite buttons: "Invite a new player: you both get a Friendship Bandana."
- A **new player** who opens the game from a friend's invite link (`/f/<code>` -> `/play/?friend=DOG-XXXXX`, V219.md 3 and 7) and adds
  that friend (the add card is pre-filled, as before) is recorded by the Worker as invited by them.
  - The card never closes a window the player has open and never shows over a story scene: straight after the add in the Friends sheet it takes
    the sheet's place; from a later poll it opens only when the screen is calm (`nwCalmNow`), else a toast says it and the letter keeps it.
    Letters that a card or toast announces come without a "New mail" toast; Gerald's letters keep their line breaks.
  - With cloud save on (an email account): a card "A gift from your friend's invite!" with the **Friendship Bandana** (to the
    Wardrobe) and Gerald's letter "Welcome to town" (kept).
  - A guest (cloud save not on yet): a kind card and letter: "Your Friendship Bandana is waiting. It arrives as soon as you turn on cloud
    save (More, Cloud save). Nothing is lost meanwhile." The bandana arrives the next time the game starts with the account.
- The **inviter** (email account) gets the same bandana and Gerald's letter "New friends joined through your invite!" (names in the body) the next time the game
  starts (or comes back to the yard). Later friends who join bring a letter each, no second bandana. A guest inviter gets one kind letter that
  the bandana waits for cloud save.
- Never coins, never Bond, never anything that changes play. The bandana is a look only (like the Follower Star Bandana).

## 2. Friend invite gift: the Worker decides

New table `invites (new_id text primary key, inviter_id text not null, at integer not null)` (index on `inviter_id`). One row per new
player, ever.

- `POST /invite/join { code }` (bearer token, guest or email). After a successful `/friends/add` from the invite link. Checks, in order:
  - The game's **official Friends account** (V219.md) works as a friend but gives no invite gift (owner, 17 Nov): `409 official`, no row.
  - rate limits: 10 an hour per account, 30 an hour per IP, every attempt counts (`429 rate_limited`); and at most **5 new invite rows a
    Japan day per IP** (`429 rate_limited`), so one device cannot mint a pile of accounts;
  - `bad` body (not exactly `{ code }`) `400`; unknown code `404 no_code`; my own code `400 self`;
  - we must be friends now (the add went through): else `409 not_friends`; the inviter official: `409 official`;
  - I am a **new account**: `users.created_at` at most **7 days** ago (`INV_NEW_DAYS`), and the inviter's account is older than mine
    ("they were here first"): else `409 not_new`;
  - one row per new player: a second call `409 used` (unique `new_id`).
  - `200 { ok: true, gift: 'now' | 'later' }`: `now` for an email account, `later` for a guest.
  - The game treats `no_code`, `self`, `bad`, `not_friends`, `official`, `not_new` as final (`S.fi.join = 'no'`); `used` as the gift; anything
    else (offline, 401, 429, 5xx, an older Worker's `404 not_found`) keeps `S.fi.link` and asks again on the next start or log in. An add that
    answers "already friends" from the invite link still sends the join.
- `GET /invite/gifts` (bearer token; 120 an hour): an email account gets
  `{ mine: { name: [a,b] | null } | null, joined: [{ t, name: [a,b] | null }] }` (no times: V219.md, never a clock time). `t` is an opaque
  token for the row (a hash of the two accounts, 16 hex, never a user id); the game keeps the tokens it thanked (`S.fi.thx`) and thanks each once,
  so a guest invitee who turns on cloud save later (and sorts before newer friends) is still thanked. `mine` is my own row (I was invited); `joined` is
  the new players I invited **who have cloud save on now** (email accounts), oldest first, **at most 10** (`INV_CAP`: the inviter's cap;
  the 11th new player still gets their own bandana). A guest gets `{ guest: true, mine: 0|1, joined: n }`, never names.
  Names are friend names (two Dog Card words), never a user id, email or exact account time.
- Farming: no coins at all, the bandana is one look (a second credit gives no second bandana), one row per new account, 7-day-new accounts
  only, the inviter older, the per-IP daily cap, and credits only for new players with an email account.
- `btTidy()` runs from the Worker's `tidy()` (1 in 10 of its runs, about 1 in 1,000 requests; never on a v2.30 route's path) and drops rows
  whose new player or inviter account is gone (a deleted account).

## 6. Shared town goal: the Worker

Tables `town_goal (month text primary key, n integer, goal integer, done_at integer)` and
`town_goal_users (month, user_id, n, primary key (month, user_id))` with the index `town_goal_users_user (user_id, month)` (final review: the
`owed` lookup of `GET /town/goal` scanned the whole table on every game load without it). Months are Japan months (`YYYY-MM`).

- `POST /town/goal { n }` (bearer token, **guest or email**): `n` an integer 1..40, else `400 bad`. At most one post every 2 minutes
  per account (`429 rate_limited`). Then the add is clamped by two daily caps (Japan day): **150 per account** and **5,000 per IP** (review
  17 Nov: a school or a carrier's shared IP is many players; was 600). The IP's share is one atomic upsert ... `returning n` (its row counts what
  was offered, so `n - want` is what came before); the account is charged only what was taken. `took` is the counted part (0 when a cap is
  full, still `200`); the account's month row is made even then (`part: true`). `200 { ok, took, month, goal, n, done, mine, part }`.
- `GET /town/goal` (a token is optional; 120 an hour **per account** with a token, per IP without): `{ month, goal, n, done, mine, part,
  last: { ... }, owed: [...] }`; `mine` 0 and no `owed` without a token. `owed`: the account's months that reached the goal (the last 12), so a
  treat bag earned before two or more months away still comes. The town's totals are cached 60 s in the isolate (`GL_CACHE_S`; a POST refreshes).
- Why guests count too: almost every itch.io player is a cloud guest (`POST /guest`, 60 an hour per IP), so an email-only goal would
  leave most of the town out. The **per-IP daily cap** is the real ceiling (a pile of guest accounts on one IP adds at most 600 a day),
  the per-account cap stops one script, and nothing of value rides on the count (a treat bag once a month). Players without any
  cloud (the claude.ai copy) neither count nor see the board.
- `btTidy()` (from `tidy()`) drops `town_goal_users` rows of deleted accounts and months older than 13 months.

## 7. Shared town goal: the game

- `S.goal = { q: 0 (belly rubs waiting to be sent, at most 200), at: 0 (last post), got: [months gifted], last: null (the last answer),
  sent: { 'YYYY-MM': n } (what this save added, for the sheet), miss: '' (the month whose "so close" letter was sent) }`.
- A post at most every 5 minutes (`GL_EVERY`), only with something waiting, only while `btOn()` and a cloud token; also on page hide.
  At most 40 a post; what the Worker did not take beyond its caps is dropped (never retried forever).
- The gift: on start, on the yard and after a post, when the answer says a month (this, last, or one in `owed`) is `done`, the save took
  part (`mine > 0` or `part`) and the month is not in `got`. "So close!" only for a month before the **Worker's** month (never the device clock).
