# Cloudflare login (planned release after v2.7)

The owner's decisions (13 Oct 2026, choice window):

- **Swap the login and cloud save from Supabase to Cloudflare.** The title screen stays exactly as it is: Log in / Make an account / Play as guest, email plus own password, no emails ever sent, and Export / Import save codes.
- **When:** after v2.7 ships, as its own small release, before v2.8 (Winter + Japan).
- **Old accounts move over:** same email and password, nothing lost.
- **Sync on open, no live push:** the save syncs on every change (as now, about 2 s after real input), on game open and on focus. No Realtime or Durable Objects.

## Shape (for the team that builds it)

- **Worker** `pawhaven-api` (`cloudflare/worker.js`, `cloudflare/wrangler.toml`) on `workers.dev`, with a **D1** database `pawhaven`:
  - `users (id, email unique null, pw_hash, pw_salt, created_at, guest int)`,
  - `sessions (token_hash, user_id, created_at, last_seen)`,
  - `saves (user_id pk, data, rev, changed_at, device, updated_at)`, `save_backups (...)`, the same fields as `supabase/schema.sql`.
- **Passwords:** PBKDF2-SHA256 with Web Crypto (100k iterations, a 16-byte salt). Never stored or logged in plain text. Login is rate-limited per IP and per email.
- **Sessions:** a random 32-byte bearer token. Only its SHA-256 is stored. The client keeps the token in `localStorage['pawhaven_cf_auth']`.
- **Guests:** `POST /guest` makes a guest user with no email. "Make an account" on a guest adds email and password to the same user, the way the anonymous Supabase upgrade works now.
- **Endpoints:** `/guest`, `/register`, `/login`, `/logout`, `/me`, `GET/PUT /save` (rev and changed_at conflict rule unchanged, the loser goes to `save_backups`), `/backups`. CORS only for the game's origins: doodledoggo.app (and www), GitHub Pages, localhost, and the itch.io game frame (https://html-classic.itch.zone and https://html.itch.zone). The itch.io copy needs this so players there can log in. The claude.ai artifact stays cloud-off.
- **Moving old accounts (lazy, no password export):** when `/login` gets an email it doesn't know, the Worker tries Supabase's password grant with the **public** publishable key. If Supabase accepts, the Worker makes the Cloudflare user with a fresh PBKDF2 hash of that same password, reads that user's `saves` row with the user's own Supabase token, stores it, and marks the email migrated. No secret key and no hash export are needed. Guests never had a password: their save is already on the device and uploads to the new guest account on first start. Keep Supabase on for about 3 months, then switch it off.
- **Client:** `game/src/22b_cloud.js` keeps its public API and the title UI. Only the transport changes, from supabase-js to `fetch` against the Worker. Drop the Realtime channel and keep the focus pull. `22b_cloud_config.js` holds only the Worker URL. Update `test_cloud.js`, `test_account.js` and the mock (`window.__pawCloudMock`) to fake the Worker.
- **Tests:** a node test for the Worker (Miniflare or `wrangler dev --local` with D1 local), plus the existing cloud and account suites against the mock.

## What the owner needs to set up before this starts

1. A Cloudflare account (free plan is enough: Workers + D1).
2. A Cloudflare API token with **Workers Scripts: Edit** and **D1: Edit** on the account, plus the **Account ID**. Add them to the cloud environment (environment menu, Edit, Network secrets) as `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Never paste them into chat.

## As built (v2.8.1, 16 Oct 2026, CLOUDFLARE team)

- **Worker** `pawhaven-api` at https://pawhaven-api.ansonyuen0108.workers.dev, D1 `pawhaven` (`d6bacd44-9f88-4c66-9ef6-ca15417a5c97`). Deploy: `bash tools/cf_api_deploy.sh` (REST API, no wrangler needed; makes the database if missing and re-applies `cloudflare/schema.sql`, which is safe to repeat). Live check: `bash tools/cf_api_smoke.sh` (makes one throwaway `pawhaven-smoke-*@example.com` account).
- **Endpoints** as planned, plus `POST /password` (change password), `POST /migrate` (below) and `GET /save?meta=1` (rev and changed_at only). `PUT /save` refuses a rev the cloud already has (409 `stale`), and the game then looks again, so two devices can't overwrite each other blind. Errors are short codes (`invalid_credentials`, `email_exists`, `weak_password`, `invalid_email`, `rate_limited`, `busy`) that `clErrText()` turns into the same kind messages as before.
- **Rate limits** (D1 table `rate`): log in 30 per 10 min per IP and 10 per 10 min per email, make an account 10 per hour per IP, guests 60 per hour per IP, save pushes 60 per minute per player.
- **Moving old accounts.** By password: `/login` with an email the Worker doesn't know asks Supabase once (password grant with the public publishable key), then makes the user with the **same user id**, a fresh PBKDF2 hash, the save (data, rev, changed_at, device) and up to 5 backups. Verified live on 16 Oct with a throwaway Supabase account (`pawhaven-test-cf-1792112261@example.com`, made through the public sign-up; the public API can't delete it, so remove it in the Supabase dashboard).
 By session (added): a device still logged in to Supabase sends its stored Supabase tokens to `POST /migrate` on first start, and carries over with no password typed (the hash is stored on the next typed log in). Keeping the Supabase user id means the device's save stays "owned" by the same account, so nobody sees a log-out or a moved game.
- **"Make an account" with an old email** (Game Manager, 16 Oct): before making a new user, `/register` tries the Supabase password grant with the typed password. If Supabase says yes, that old account moves over exactly as at log in (`migrated: true`), and the game treats it as a log in: the account's save loads and the guest game goes to its backups ("You already had an account with that email."). No user data is copied before Supabase says yes. Known gap: Supabase answers a wrong password and an unknown email the same way, so an old email registered with a *different* password makes a new, empty account here, and the old Supabase save can then only come back through that device's carried-over login or by hand. The email-hash list that closed this gap was dropped (no user data copied).
- **Supabase**: leave it on until about mid-January 2027 (3 months), then switch it off. To switch it off, remove `SUPABASE_URL` / `SUPABASE_KEY` from `cloudflare/wrangler.toml` and redeploy: old accounts that never logged in by then can't move over after that.
- **Client**: `game/src/22b_cloud.js` keeps its public API, the title UI and the Settings section. `CL.regPath` is now `upgrade` (the guest became the account) or `new`.
- **Tests**: `node game/run_tests.js worker` (in Node over `node:sqlite`, and in Miniflare 4 with a real local D1 when `miniflare` is installed globally; `tools/session_start.sh` installs it), and `cloud` / `account`, which now run the real Worker on a local D1 through `game/cloud_mock.js` (no network). The cloud suite adds sync on focus (no Realtime) and a device carrying its v2.8 Supabase login over.
- **doodledoggo.app** is the Worker `doodle-doggo` (`tools/cf_site.js`, `tools/cf_pages_deploy.sh`), not a Pages project: Pages and Workers-assets uploads authenticate with an upload JWT, and the cloud session's proxy overwrites that header with the API token, so they fail with 401 from a Claude session.

## v2.8.2 "Account safety" (16 Oct 2026, owner's requests)

- **One email, one account.** `/register` answers 409 `email_exists` ("This email already has an account. Log in, or use Forgot your password.") for an email that has an account here, or that belongs to an old Supabase account not moved over yet. The D1 table `legacy` holds the SHA-256 of the lower-cased emails of the non-anonymous Supabase users (7 rows on 16 Oct; the 8th had moved already). The list is final, since no Supabase accounts are made after v2.8.1. A row goes when that account moves over (log in, a carried-over login, or a reset). This replaces the v2.8.1 "As built" note about Make an account trying the password with Supabase: that shortcut is gone, and logging in moves an old account.
- **Forgot password.** "Forgot your password?" under Log in (the title sheet and Settings) opens a form with the email already typed. `POST /forgot` always answers `{ ok, mail }` the same way whether or not the email has an account (`mail: false` only while no email service is set up, and then the game says resets by email aren't on yet). Limits: 3 links an hour per email (quietly), 10 requests an hour per IP (429).
- **The link.** 32 random bytes, only the SHA-256 is stored (table `resets`), 30 minutes, single use, and only the newest link works. The email links to `https://doodledoggo.app/reset?token=…`, a page of the introduction site (`site/reset.html`, owner's choice: the game is played on itch.io). The page drops the code from the address bar, asks for the new password twice, calls `POST /reset` (which sets the new PBKDF2 hash and logs out every session of the account), logs its own new session out again, and says "All set! Go back to the game on itch.io and log in." with a button to https://an9ou.itch.io/doodle-doggo.
- **An old Supabase account not moved yet.** `/forgot` asks Supabase's public `/auth/v1/recover` to send its own reset email, with `redirect_to` `https://doodledoggo.app/reset`. Its link opens the reset page with a recovery login (`#…type=recovery`), and `POST /reset` with `sb_token` moves the account over with the new password, save and backups included. Nothing is copied before that. For this to reach players, Supabase needs custom SMTP (its built-in mailer only sends to the project's team), with https://doodledoggo.app/reset in its redirect URLs: see the owner steps below. Without them, those few accounts can still move over by logging in with their old password.
- **Email.** Resend, from `Doodle Doggo <noreply@doodledoggo.app>`, with plain, friendly copy (the subject is "Your Doodle Doggo password link", and Noodle says hi). The key is the Worker secret `RESEND_API_KEY`. Tests use a fake Resend (`fakeMail` in `game/cloud_mock.js`).
- **Owner setup (once):**
  1. Make a free account at resend.com (sign up with the owner's email).
  2. Resend → API Keys → Create API key, with permission **Full access** (the script adds the domain with it). Copy it once.
  3. Claude environment settings → Environment variables: add `RESEND_API_KEY` with that key (never paste it into chat), then start a new session for the CLOUDFLARE team.
  4. That session runs `bash tools/resend_setup.sh`. It adds doodledoggo.app to Resend (Tokyo region), adds the DNS records Resend asks for to the Cloudflare zone (DKIM `resend._domainkey` TXT, the `send` MX and SPF TXT, plus `_dmarc`), asks Resend to verify, and stores the key as the Worker secret only once the domain is verified. If the Cloudflare token lacks Zone DNS: Edit, it prints the records to add by hand (Cloudflare dashboard → doodledoggo.app → DNS → Add record, proxy off).
  5. Optional, for old Supabase accounts: Supabase → Authentication → Emails → SMTP Settings: host `smtp.resend.com`, port 465, user `resend`, password = the Resend key, sender `noreply@doodledoggo.app`, name Doodle Doggo. Authentication → URL Configuration: add `https://doodledoggo.app/reset` to the redirect URLs.
- **The introduction site** (`site/`, owner's choice on 16 Oct): home (logo, Noodle, tagline, what it is, six features, four screenshots, Play free on itch.io), `/privacy` (from `docs/itch/PRIVACY.md`, updated for the password emails, contact placeholder kept) and `/reset`. Fonts are self-hosted (Caveat, Patrick Hand), screenshots are WebP, and nothing loads from anyone else (CSP `default-src 'self'`, the reset page may also call the Worker). It is served by the Worker `doodle-doggo` (`tools/cf_site.js`, 0.84 MB), and the Instagram link is a placeholder until the account URL is known. Test: `node game/run_tests.js site`. Deploy, after the owner's go-ahead: `bash tools/cf_pages_deploy.sh`.
